Enquiry handling and privacy

  1. The visitor can call, use the existing direct WhatsApp/email links, or choose a demonstration/quotation.
  2. The composer preselects the current service. Name, mobile, organization, service, city, requirement and consent are required; email is optional.
  3. Preparing the message performs local validation and shows a text-safe preview. It does not submit an enquiry.
  4. The visitor explicitly opens WhatsApp or an email draft, reviews the recipient/message and sends through that channel. Opening the channel is not evidence of receipt.

There is no new server-side form endpoint, lead database, submission REST exposure or CRM. The theme makes no form-data fetch request and stores no enquiry in cookies, local storage or public metadata. Consequently it introduces no new server submission queue for spam. The existing communication provider's abuse controls and the business inbox still apply. Do not treat browser validation as security for a future backend: if an existing secure form/CRM is connected later, use its server-side validation, permissions, rate limiting and anti-spam controls.

Consent revocation or input edits invalidate the preview and clear prepared handoff URLs. Message preview uses text content, not HTML. The composer is hidden if JavaScript is unavailable and direct contact alternatives remain. A privacy-policy link appears only when WordPress has a published policy configured. The owner should review that policy for the actual website and external communication providers; no unverified legal policy was published by this work.
