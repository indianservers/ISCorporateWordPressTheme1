Partner Signup

Theme 1.0.45 and Indian Servers Forms 1.2.3 implement the partner expression-of-interest application. The source projects are ISCorporateWordPressTheme1 and the neighbouring WPISForms/indian-servers-forms. Both updates are needed. This delivery is local code and disposable WordPress verification, not a production deployment.

Destinations and installation

  1. Back up the installed theme, IS-Forms plugin and WordPress database.
  2. Update the existing indian-servers-forms plugin folder to 1.2.3 and the existing theme to 1.0.45. Keep their installed directory names and the existing plugin active; do not install an unrelated forms plugin.
  3. Visit the WordPress administration area as an administrator. The versioned, locked, idempotent setup creates one “Partner Signup” form and one published “Partner Signup” page containing [isf_partner_signup]. An existing page or unrelated form with the same slug is preserved and an administrator notice explains the conflict. Existing drafts are not automatically published.
  4. If an existing published privacy policy is available, select it in Settings → Privacy so the application displays its link. Applications can also be submitted without a configured policy URL; accuracy and contact consent remain required. The implementation does not invent or publish a policy.
  5. Check /become-our-partner/ → “Submit your details” → /partner-signup/. The CTA uses WordPress URL helpers and opens in the same tab. The highlighted signup action appears directly below the partner-page title and also floats at the bottom of the viewport. WhatsApp discussion and email links remain.
  6. Review IS-Forms notification recipients in the existing form builder, test delivery on staging, then purge the site's page/CDN caches.

Expected production destination: https://indianservers.com/partner-signup/. It is available after the code is deployed and setup runs. The existing page did not contain a “Submit your details” CTA; the application action was first introduced in that card and has now moved to the hero, with a floating copy available while scrolling. Other partnership contact links were retained.

Storage and migration

Partner Signup is registered as the partner-signup form slug with settings.form_type = partner_signup. Its definition uses the existing {prefix}is_forms table. Applications use the existing entry repository, {prefix}is_form_entries, and {prefix}is_form_entry_meta. Structured answers are existing metadata rows, not a separate application database. They include the form type, reference, applicant/contact/business/location details, all relevant answers and consent choices. The entry holds the timestamp and application status.

Database version 1.2.0 uses the plugin's existing dbDelta migration to add nullable submission_key VARCHAR(64) and a unique index to is_form_entries. Existing rows retain NULL, allowing all historical entries and ordinary forms to coexist. No tables or existing columns are removed. Partner saves use a transaction through the existing repository and require all metadata writes to succeed. A final completeness marker prevents premature confirmation. MySQL transactional guarantees assume the normal InnoDB storage engine.

Form answers and the schema live in includes/class-isf-partner-schema.php. Generic form-builder saves preserve the application's schema and type; notification settings remain editable. Either [isf_partner_signup] or the existing [is_form id="FORM_ID"] mechanism renders this application. It also works through the plugin's existing form block. Page builders can embed the shortcode; assets are enqueued by the renderer and preloaded on the created page.

Administration

WordPress admin → Indian Servers Forms → Partner Signup lists Reference, Date, Applicant, Type, Company, Mobile, Email, Location, Products and Status. It uses the existing repository's search, status/date filters and count/pagination functions. Click a reference for answers grouped by step and status history. Statuses: New, Under Review, Contacted, Approved, Not Proceeding. Only administrators with manage_options and the entry-specific nonce can change status. Concurrent changes are checked before updating. The existing logger records the actor and status change.

Partner applications also appear in the existing Entries list and its form filter. Partner detail links use the grouped application view. Generic “mark read/unread/spam” actions do not overwrite application workflow statuses. Existing CSV export includes all partner metadata and status and escapes spreadsheet formula prefixes in headings and values. Existing exports are limited to 5,000 entries per filtered export, following the plugin's current behaviour.

Behaviour, privacy and security

  • Six steps, conditional Individual/Company and existing-business paths, per-step validation, preserved back navigation, grouped review with edit buttons, required accuracy/contact declarations and a separate unchecked marketing opt-in.
  • The existing plugin's save/resume is browser-local, not a server draft service. The application follows that model with an explicit save/restore action, a scoped storage key, clear-draft control and seven-day expiry. It does not continuously write personal information or automatically restore it. Confirmed submission clears its local draft.
  • An uncached AJAX bootstrap fetches a fresh WordPress nonce and signed start token for cached pages and logged-out visitors. A database-unique retry key is kept through retries. Success is shown only after complete storage is confirmed. Network errors retain the current answers.
  • Server field allowlists, option allowlists, scalar/array validation, maximum lengths, email/phone/URL/year/GSTIN checks, a 64 KB request limit and 50 KB answer limit. Irrelevant conditional data is discarded. No identity documents, banking details or uploads are accepted.
  • Honeypot, signed minimum submission time, ten successful applications per source per hour and three per email per hour. Rate keys are temporary salted hashes; partner entries retain no raw IP, user agent or referrer. The existing notification logger is filtered to keep contact details out of partner log context.
  • Existing email notifications run after storage. Failure is logged without exposing personal information and does not discard the application. Existing entry-reading REST endpoints remain restricted to administrators; no public submission-reading endpoint was added.
  • The supplied original Indian Servers PNG is bundled without alteration as the fallback logo; the configured WordPress logo takes precedence. All illustration/icon assets are local SVGs. Form CSS/JavaScript is scoped to the application; the theme's floating conversion tools are suppressed only on the application page/shortcode.

Product labels and terms

Unlisted College Management, Financial Management and Association/Club Management interests are explicitly labelled as enquiries. No fees, commissions, guaranteed earnings, available/exclusive territories or binding partnership terms are invented.

Validation and UI update — Forms 1.2.1

Mobile, WhatsApp and postal format rules are defined once in PHP and supplied as JSON to the browser. Indian mobiles require ten digits starting with 6–9; pasted +91 / 0091, spaces, hyphens and a leading trunk zero are normalized. Calling codes use + and one to three digits. International numbers are limited to fifteen digits including the calling code. These are format checks, not proof that a number exists or belongs to the applicant. References: Indian telephone metadata and ITU E.164.

Indian PINs use six digits and cannot begin with zero. US ZIP/ZIP+4, Australian four-digit postcodes and Canadian postal formats have dedicated checks; other countries retain an alphanumeric fallback. The UAE postal field is optional. No location is inferred or sent to a third-party lookup service. References: India Post, USPS, Australia Post, Canada Post.

An alternate WhatsApp number requires its international prefix, and becomes required if WhatsApp is the preferred contact method and “same as mobile” is unchecked. Names must contain a Unicode letter; malformed email dots and field lengths are checked. Required declarations, conditional fields, URL checks, GSTIN format and future-year rejection remain in force.

The profile now has contact/location/preference groups, compact calling-code and mobile fields, linked examples, errors on leaving a field, correction feedback, current-step progress and completion indicators. Multi-select options use selectable chips. Mobile inputs use at least 16px type, and the existing reduced-motion preference is respected.

Suggested next enhancements: verified PIN-to-city/state lookup with a manual override; optional OTP to establish mobile ownership; a printable confirmation summary; and a concise help panel explaining business-approved partnership roles. These are suggestions, not activated services or new partnership terms.

No database migration or theme re-upload is needed for this fix.
